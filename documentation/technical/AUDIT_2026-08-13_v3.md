# Full Project Audit — 2026-08-13 (v3)

**Scope:** Follow-up security sweep after the `AUDIT_2026-08-13_v2.md` fixes (commit `9721d0a`). Re-verified those fixes hold, then went deeper into areas not covered by v1/v2: RPC function permission grants (`GRANT`/`REVOKE` history across all migrations), `SECURITY DEFINER` search_path hardening, XSS surfaces, and hardcoded-secret sweeps of both the working tree and full git history.

**Status of prior fixes:** All four `AUDIT_2026-08-13_v2.md` critical/high items are confirmed still in place in the codebase (RLS policies, trigger, R2 removal, npm audit clean, Dockerfile). `tsc --noEmit` clean, `vitest run` 35/35 files (137/137 tests), `npm audit` 0 vulnerabilities.

## 🔴 Critical — worse than anything found in v1/v2, currently exploitable by anyone, no login required

### 1. `create_user_invitation` is executable by unauthenticated visitors and its internal role check is bypassable when no account exists — complete unauthenticated-to-admin takeover

- **Where:** `supabase/migrations/20260806000001_fix_create_user_invitation_permissions.sql:52` (the live grant), function body in the same migration.
- **What happened:** This function's `EXECUTE` grant was changed **five times** across the migration history, flip-flopping between correct and broken:
  1. `20260729000005` — `REVOKE ALL ... FROM public, anon; GRANT ... TO authenticated;` (correct)
  2. `20260805000000` — `GRANT ... TO anon, authenticated, service_role;` (broken)
  3. `20260806000000` — `REVOKE ALL ... FROM public, anon; GRANT ... TO authenticated;` (fixed again)
  4. `20260806000001` — `GRANT ... TO authenticated, anon, service_role;` (broken again — **this is the last one applied**, and nothing since has touched it)
- **The exploit chain:**
  1. The function's own authorization check is: `IF v_user_account_id IS NOT NULL AND v_role NOT IN ('principal','admin') THEN RAISE EXCEPTION 'Only managers can invite users.'`. This was clearly written assuming the caller is authenticated. For an anonymous caller, `auth.uid()` is `NULL`, so `get_current_user_account_id()` returns `NULL`, so `v_user_account_id IS NOT NULL` is **false**, so the `AND` short-circuits and the exception never fires. An unauthenticated caller sails straight through the only role check in the function.
  2. Agency resolution also falls back silently: `get_current_agency_id()` also returns `NULL` for an anonymous caller, so the function falls back to `SELECT id FROM public.agency LIMIT 1` — i.e. whatever agency happens to be first in the table, almost certainly the real production tenant in a single-agency deployment like this one.
  3. The function then inserts a real row into `user_invitation` with `role = p_role` — an enum parameter the caller fully controls, including `'admin'` — and returns the raw invitation token to the (still-anonymous) caller.
  4. The caller signs up normally at `/register` (`supabase.auth.signUp`, `src/routes/register.tsx:111`) using the same email address they just invited, which is trivial since it's their own email.
  5. The caller calls `accept_user_invitation(token, ...)` — this one _is_ correctly gated (`revoke all ... from public, anon` + an internal `auth.uid() IS NULL` check), but by this point the caller is authenticated (step 4), so it succeeds and creates a `user_account` row with `role = 'admin'`.
  6. The attacker is now a full administrator of the agency, having never had any prior account or credential.
- **Impact:** This requires nothing but the public Supabase anon key, which is embedded in every client bundle by design — i.e. any visitor to the site's homepage. It's a strictly worse, easier vulnerability than the `user_account` privilege-escalation hole already fixed in `9721d0a`, because it needs no existing account at all.
- **Fix:** `REVOKE EXECUTE ON FUNCTION public.create_user_invitation(text, public.user_role) FROM anon;` — the function should only ever be callable by `authenticated` (its own internal logic already assumes that). Also consider hardening the function body itself to `RAISE EXCEPTION` explicitly when `v_user_account_id IS NULL`, rather than relying solely on the GRANT to keep anonymous callers out — belt-and-suspenders, since this exact function has now had its permissions flip-flipped five times across five migrations.

## 🟡 Medium

### 2. 16 `SECURITY DEFINER` functions are missing `SET search_path`

- **Where (final/live definitions, one per function):** `log_audit_event`, `adjust_user_storage_usage`, `admin_archive_old_deals`, `admin_bulk_reset_commission`, `admin_bulk_retire_users`, `admin_deactivate_idle_agents`, `admin_empty_recycle_bin`, `create_deal_full`, `generate_daily_notification_digests`, `get_current_user_account_id`, `get_current_user_role`, `is_principal_or_admin`, `queue_tenant_rent_reminders`, `register_new_agent`, `trigger_deal_stage_whatsapp_notification`, `update_user_storage_quota`.
- **What:** Unlike their sibling functions (`is_manager()`, `get_current_agency_id()`, `can_access_deal()`, the `protect_user_account_sensitive_fields` trigger — all of which correctly `SET search_path = public, pg_temp`), these 16 have no `search_path` pinned on a `SECURITY DEFINER` function. This is the exact pattern Postgres/Supabase's own linter (`supabase db lint`, which this repo's CI already runs at `.github/workflows/ci.yml:131`, but only at `--level warning`, so it doesn't fail the build) flags as a hardening risk: a `SECURITY DEFINER` function runs with its owner's privileges, and without a locked `search_path`, any unqualified identifier inside it resolves against whatever `search_path` the _calling session_ has set, which an attacker can manipulate before calling the function.
- **Actual exploitability here:** Checked the body of every function in this list that touches sensitive operations (`admin_archive_old_deals`, `admin_deactivate_idle_agents`, `admin_empty_recycle_bin`, `create_deal_full`, `register_new_agent`, `get_current_user_role`, `get_current_user_account_id`, `is_principal_or_admin`) — every table and function reference inside them is already schema-qualified with `public.`, which is the main practical mitigation for this class of bug. So this is a hardening gap rather than a demonstrated live exploit today, but it's inconsistent with the rest of the codebase, trivially easy to fix, and one careless future edit (an unqualified reference slipped into any of these) would silently reopen a real vulnerability with no test or CI failure to catch it.
- **Fix:** Add `SET search_path = public, pg_temp` (or `public, extensions, pg_temp` for the ones using `pgcrypto`/`digest()`) to all 16, matching the pattern already used correctly elsewhere. Consider bumping the CI lint step from `--level warning` to `--level error` once these are fixed, so this class of regression fails the build going forward instead of silently passing.

## 🟢 Low / Informational

- **`register_new_agent` is dead code.** `REVOKE ALL ... FROM public, anon, authenticated` with no subsequent grant means literally nobody can call it anymore, and nothing in `src/` references it — it was superseded by the invitation-based registration flow. Not a vulnerability (it's unreachable), just cleanup debt.
- **No XSS risk found.** The only `dangerouslySetInnerHTML` in the codebase is `src/components/ui/chart.tsx` (standard shadcn/ui chart-theming boilerplate) — its inputs (`id` from `React.useId()`, `config` colors) are developer-supplied when building a chart, never derived from user-submitted or database-sourced content anywhere in this codebase.
- **No hardcoded secrets found**, in the current working tree or anywhere in git history — `git log --all --diff-filter=A --name-only -- "*.env" ".env*"` shows only `.env.example` (placeholders) was ever committed.
- **The invitation system's other `anon`-granted functions are legitimately safe on inspection:** `validate_user_invitation` (token+email match required, boolean-only return, no enumeration surface), `prepare_invited_registration` (same token+email gating), `submit_public_lead` (intentionally public lead-capture form), `get_status_request`/`submit_conveyancer_status` (the magic-link conveyancer portal, already reviewed positively in v1), `get_current_transfer_duty_brackets` (public reference data). None of these needed changes.

1. **Immediately:** Revoke `anon` execute on `create_user_invitation` (#1) — this is more urgent than anything fixed in the previous pass, since it requires no prior account at all.
2. **This week:** Add `SET search_path` to the 16 functions listed in #2.
3. **Ongoing:** Once #2 is fixed, raise the CI `supabase db lint` level from `warning` to `error` so this class of issue fails the build automatically.
4. **Whenever convenient:** delete the dead `register_new_agent` function and its now-orphaned migration references.
