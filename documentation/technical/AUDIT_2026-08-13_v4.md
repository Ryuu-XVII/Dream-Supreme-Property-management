# Full Project Audit — 2026-08-13 (v4)

**Scope:** A different angle than v1–v3, which focused on `user_account`/`user_invitation` RLS and RPC permission grants. This pass systematically checked **every one of the 65 tables** in the schema for RLS coverage (not just the two already reviewed), plus webhook signature verification and storage path/upload validation.
**Method:** Extracted every `CREATE TABLE`, `ENABLE ROW LEVEL SECURITY`, and `CREATE POLICY`/`DROP POLICY` statement across all 58 migration files, replayed them in applied order (including one dynamically-generated policy loop that a naive static search would miss), and manually verified the resolved final state for anything that looked underprotected or overprotected. No live database access was used or available — this is a static analysis of the migration files as committed.
**Status of prior fixes:** `9721d0a` fixes confirmed still in place; `create_user_invitation`'s `anon` grant (v3 finding, not yet fixed per your instruction to skip it) is still present as documented.

## Result: no new critical or high findings

This pass came back clean relative to v1–v3. Specifically:

- **All 65 tables have RLS enabled.** None were found running without RLS at all (which would mean fully open to the PostgREST API by default).
- **No other table has the `USING (true)` / `WITH CHECK (true)` wide-open pattern.** A full replay of every `CREATE POLICY`/`DROP POLICY` statement in applied order, across every table, found the pattern contained to exactly the two tables already identified and fixed in `9721d0a` (`user_account`, `user_invitation`).
- **Investigated and resolved a false alarm:** `checklist_item`, `deal_participant`, `deal_party`, `deal_stage_history`, `suspensive_condition`, `offer`, and `bond_application` initially appeared to have zero policies (which would mean they're inaccessible to any client query, a functional bug). On closer inspection they're covered by a `DO $$ ... EXECUTE format(...) $$` loop in `20260729000005_operational_hardening.sql:278-302` that dynamically creates a properly agency-scoped `"Accessible deal child records"` policy (`using (public.can_access_deal(deal_id))`) for all seven tables at once — a static text search misses this because the policy names/tables are built from a Postgres array loop rather than appearing as literal `CREATE POLICY` text. `can_access_deal()` was already reviewed positively in v3. No issue.
- **`status_request_token`** is the one table with genuinely zero table-level policies, but it's never queried directly from the client (`grep` confirms no `.from("status_request_token")` anywhere in `src/`) — it's only touched through the conveyancer-portal RPCs (`get_status_request`, `submit_conveyancer_status`, `create_status_request`) already reviewed positively in v1/v3. Correct by design.
- **Upload path / storage authorization:** `uploadFileToR2` (now `uploadFileToR2` → Supabase Storage, per the v2 fix) builds paths as `${agencyId}/${dealId}/${uuid}-${filename}`. Even if a malicious client tampered with the `agencyId` segment client-side, the `storage.objects` INSERT policy (`supabase/migrations/20260730000001_secure_storage_buckets.sql`) independently re-derives the caller's real agency via `get_current_agency_id()` server-side and rejects any mismatch — client-supplied path segments can't be used to write into another tenant's folder.

## 🟢 Low / Informational

### Dead/unwired webhook receiver code

- **Where:** `src/services/portalWebhookService.ts` (`processPortalLeadWebhook`).
- **What:** This function is written as if it handles an inbound webhook from an external property-portal lead source (Property24-style syndication), inserting directly into `lead_capture` and triggering round-robin assignment with **no signature/source verification of any kind**. It is never imported or called anywhere else in the codebase (`grep` confirms zero other references) — it's dead code, not a live vulnerability today.
- **Why it's worth flagging now rather than later:** this is a Vite SPA with no server-side routes, so this function _cannot_ actually receive an external webhook POST in its current form regardless of whether it's wired up — a real integration would need a separate server-side function (Supabase Edge Function, Cloudflare Worker, etc.) that verifies the portal's signature/secret before calling into Supabase, not client-bundled code. If this ever gets connected to a real feed, build the signature check into that server-side layer first — don't just start importing/calling this function from a route.

### No inbound WhatsApp webhook handling in this repo

- Checked `src/services/whatsappGatewayService.ts` for webhook/signature handling — found none. The service is outbound-only (queues messages to send), consistent with there being no server-side surface in this repository to receive Meta's inbound webhook callbacks. Nothing to fix here; noting it so any future inbound-webhook work knows to also live server-side with proper `X-Hub-Signature-256` verification, not in this client bundle.
