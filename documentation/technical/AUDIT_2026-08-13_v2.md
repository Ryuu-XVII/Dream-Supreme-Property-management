## 🔴 Critical — active security incident, fix before further production use

All three critical findings from the prior audit are **still unpatched** as of this commit. Re-verification found them to be worse than originally described.

### 1. `user_account` privilege escalation — confirmed, and the trigger is a complete no-op

- **Where:** `supabase/migrations/20260811000007_allow_authenticated_sensitive_field_updates.sql` (the `protect_user_account_sensitive_fields` trigger), combined with the `user_account` UPDATE policy in `supabase/migrations/20260811000006_fix_admin_agency_null_rls.sql`.
- **What:** The trigger function's `IF` block returns `new` when any of several bypass conditions is true (`auth.role() = 'authenticated'`, `auth.uid() IS NOT NULL`, etc.) — but if **none** of them are true, execution falls through to an unconditional `RETURN new;` on the very next line anyway. The function has no code path that ever blocks an update; the "check" is entirely decorative.
- **Combined with:** the RLS UPDATE policy's `USING (... OR auth.role() = 'authenticated')` and `WITH CHECK (true)`.
- **Impact:** Any authenticated agent can run `UPDATE user_account SET role='admin' WHERE id=<self>`, or rewrite another user's `agency_id`, `commission_pct`, or `status`, and immediately gain administrative privileges or cross-tenant access. There is no server-side check standing between any logged-in user and full control of every user record in the system.
- **Fix:** Rewrite the trigger to actually branch — `RAISE EXCEPTION` (or skip the sensitive-field change) when none of the legitimate bypass conditions hold — and restore a real role check (`get_current_user_role() IN ('admin','admin_agent')`) in both the trigger and the RLS `WITH CHECK` clause.

### 2. R2 storage secret key is shipped to every browser

- **Where:** `src/lib/storage.ts:34-71` (`getR2Credentials`), reading `VITE_R2_ACCESS_KEY_ID` / `VITE_R2_SECRET_ACCESS_KEY` via `import.meta.env`.
- **What:** Unchanged since the last audit. Vite inlines every `VITE_`-prefixed variable into the shipped client bundle, so if these are configured in production, the R2 bucket's IAM secret key is embedded in JS that any site visitor can extract from devtools.
- **Impact:** Full read/write/delete access to the `dream-supreme-documents` bucket for anyone who opens devtools, completely bypassing `verifyStorageAccessAuthorization` (client-side only).
- **Note:** `.env.example` still only ships placeholder values (verified — no real secrets committed to the repo), so exposure depends entirely on how production env vars are actually configured on the hosting platform. If a real key is set there under a `VITE_` prefix, it is live in the shipped bundle today.
- **Fix:** Move all R2 operations (presigning, delete, authorization) into a server-side edge function or Postgres RPC. Never prefix secret keys with `VITE_`.

### 3. `user_account` is fully world-readable across every tenant

- **Where:** `supabase/migrations/20260811000008_fix_user_account_select_rls.sql:8-9`.
- **What:** `CREATE POLICY "Users can view user_account" ... FOR SELECT USING (true);` — no `agency_id` scoping, no auth check beyond being logged in at all.
- **Impact:** Any authenticated agent, at any agency, can read every other user's name, email, role, `agency_id`, mobile, commission percentage, and status across the entire multi-tenant system.
- **Fix:** Scope to `agency_id = get_current_agency_id() OR auth_user_id = auth.uid()`.

### 4. NEW — `user_invitation` has the identical wide-open pattern

- **Where:** `supabase/migrations/20260811000006_fix_admin_agency_null_rls.sql:44-49` (not flagged in the prior audit).
- **What:** In the same migration that broke `user_account`, the `user_invitation` table's SELECT and UPDATE policies were also rewritten to `USING (true)` / `WITH CHECK (true)`.
- **Impact:** Any authenticated user can read or modify every pending invitation record for every agency — including, depending on schema, invitation tokens/emails used to onboard new users. Combined with finding #1, an attacker could plausibly use this to redirect or hijack an in-flight invitation.
- **Fix:** Same remediation pattern as #1/#3 — scope to the inviting agency, and add a real role check to the UPDATE policy instead of `WITH CHECK (true)`.

**Blast-radius check:** a repo-wide grep for `USING (true)` / `WITH CHECK (true)` and the `auth.role() = 'authenticated'` bypass pattern across all 57 migrations found no other affected tables. The damage is contained to `user_account` and `user_invitation`, both introduced by the same two migrations (`...000006`, `...000007`, `...000008`), all committed as part of the same change.

## 🟡 Medium

### NEW: Admin impersonation ("View Portal") is a client-side simulation, not a real security boundary

Added this session (`9ba9fc6`). Documented here as a known, accepted limitation rather than a bug:

- The feature never switches the Supabase auth session — the admin's real JWT is used for every request while "viewing" an agent's portal.
- A central guard (`src/lib/supabase.ts`) blocks `insert`/`update`/`upsert`/`delete`/`rpc`/storage-write calls client-side while impersonation is active, and the UI disables the corresponding buttons across the portal.
- **This is enforcement in the browser only.** Given finding #1 above, it's currently moot as a security boundary anyway — any authenticated agent (impersonated view or not) already has unrestricted write access to `user_account` at the database level, regardless of what the impersonation guard blocks in the client. Fixing #1 is a prerequisite for the impersonation read-only guarantee to mean anything at the data layer.
- Reads are **not** scoped to the impersonated agent's real RLS permissions — the admin's own (wider) RLS grants determine what data loads, so "View Portal" can show an admin more than the real agent would ever see, which is a UX/audit concern more than an escalation (since the admin already had that access).

## Recommended remediation order

1. **Immediately:** Fix the `user_account` trigger so it actually blocks unauthorized updates, restore a real role check in the RLS `WITH CHECK`, and scope the SELECT policy to the caller's own agency (#1, #3).
2. **Immediately:** Apply the same fix to `user_invitation` (#4) — it was broken by the same migration and is just as exploitable.
3. **Immediately:** Move R2 credential usage server-side; stop shipping the secret key to the client (#2).
4. **This week:** `npm audit fix` for the three prod advisories; add a `USER` directive to the Dockerfile's final stage.
5. **Soon:** Rewrite the three financial test files to import and exercise real service functions instead of local re-implementations.
6. **Once #1 and #4 are fixed:** the impersonation read-only guard becomes a meaningful second layer of defense rather than a moot one — no code change needed there, just sequencing.
7. **Ongoing:** consolidate on one package manager, reconcile `.env.example`, consider a thin service layer for direct-Supabase routes.
